# Race Duration Feature Design

## Overview

Add enforced time-limit functionality to races. Admins set a duration (in minutes:seconds) when creating/editing races. Participants see a countdown timer during the race. When time expires, the race auto-completes and further typing is blocked. Server-side validation prevents submission of progress after the time limit.

## Requirements

- **Admin panel**: Time picker (MM:SS format) in create/edit race forms
- **Client-side**: Countdown timer on race page; disable input when time expires
- **Server-side**: Reject progress updates if race duration has elapsed
- **Required field**: Duration is mandatory for all new races

## Database Schema

### Changes to `races` table

Add one column:
- `durationSeconds`: `integer`, nullable, default `null`
  - Stores duration in seconds
  - Nullable for backward compatibility with existing races
  - Migration generated by Drizzle ORM

### Migration

```bash
npx drizzle-kit generate   # Auto-generate migration from schema changes
npx drizzle-kit migrate    # Apply migration
```

## Admin Form Changes

### Create Race (`src/app/admin/(protected)/races/new/page.tsx`)

Add time picker below the Status field:
- Two input boxes: **Minutes** (0-999) and **Seconds** (0-59)
- Display format: "MM : SS"
- Validation:
  - Seconds: must be 0-59
  - Minutes: must be >= 0
  - Required field — form won't submit without valid duration
- Tooltip: "How long participants have to complete the race"
- On submit, convert MM:SS to total seconds and send as `durationSeconds` in request body

### Edit Race (`src/app/admin/(protected)/races/[id]/edit/page.tsx`)

- Same time picker UI as create form
- Pre-fill with current `durationSeconds` converted back to MM:SS
- When fetching race data, convert `durationSeconds` → `{ minutes, seconds }`
- On submit, convert back to seconds

### Helper Functions (`src/lib/time-utils.ts`)

New utility file with two functions:

```typescript
export function secondsToMinutesSeconds(seconds: number): { minutes: number; seconds: number }
export function minutesSecondsToSeconds(minutes: number, seconds: number): number
```

Used by both form pages to convert between display and storage formats.

## Race Page Display

### Client-Side Countdown Timer

**Location**: Race typing interface (`src/app/race/[id]/page.tsx` or race component)

Display a countdown timer showing remaining time (MM:SS format):
- Calculate remaining: `durationSeconds - (Date.now() - raceStartTime)`
- Update every 1000ms using `setInterval`
- Position: prominent, near the top or corner of the race interface

**Behavior when time expires** (remaining <= 0):
- Disable text input field
- Show "Time's up!" message
- Auto-submit any pending progress (debounced PATCH call)
- Mark race as locally completed
- Show results/completion screen

### Real-Time Sync Integration

The countdown timer runs independently of the SSE sync (which updates every 2s). Both operate in parallel:
- Timer: updates UI every 1s
- SSE: pulls participant data every 2s
- On client: respect whichever is more restrictive

## Server-Side Enforcement

### API Route: PATCH `/api/races/[id]`

When receiving a progress update (participant typing), validate:

1. Fetch the participant record (includes `startedAt` timestamp)
2. Calculate elapsed: `Date.now() - participant.startedAt`
3. Get race `durationSeconds`
4. Check: `elapsed >= durationSeconds`
   - **If expired**: Return `400 Bad Request` with `{ error: "Race time limit exceeded" }`
   - **If time remaining**: Process update normally

### Response Handling (Client-Side)

When client receives 400 with "time limit exceeded" error:
- Stop sending further progress updates
- Show "Time's up!" to user
- Mark race as completed locally
- Disable input if not already disabled

## Data Flow

1. **Create race**: Admin enters title, text, MM:SS duration → converted to seconds → stored in DB
2. **Join race**: Participant starts → `startedAt` recorded, client starts countdown
3. **Race in progress**: 
   - Client timer counts down every 1s
   - Client debounces progress PATCH calls (300ms)
   - Server validates each PATCH against elapsed time
4. **Time expires**:
   - Client: timer reaches 0, input disabled, "Time's up!" shown
   - Server: rejects any further PATCH with 400 error
   - Race marked completed

## Error Handling

- **Client-side validation**: Seconds out of range (0-59), negative minutes → show validation error, prevent submit
- **Server-side validation**: Time limit exceeded → return 400, client shows "Time's up!"
- **Edge case**: Participant's device clock out of sync → client may show input disabled before server agrees (acceptable; server is authoritative)

## Testing Considerations

- Form validation: MM:SS constraints, required field
- Countdown timer: accurate tick rate, correct remaining calculation
- Time expiry: input disables, message shows, subsequent submissions rejected
- Server validation: PATCH rejected after elapsed time, with appropriate error

## Future Enhancements

- Pause/resume timer (not in scope)
- Variable durations per race (already supported; just form UI concern)
- Client-side grace period for network latency (not in scope)
